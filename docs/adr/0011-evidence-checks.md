# ADR 0011: 보고 내용을 하네스가 대조하는 검사(할루시네이션 감소)

- 날짜: 2026-11-17
- 상태: 결정 (사용자 목표: 할루시네이션·사용량을 줄이고 결과물을 만드는 하네스)

## 배경

G2(변경 대조)·G3(하네스가 직접 실행한 테스트)·G4(독립 리뷰)는 있었지만, 보고서의 다른 주장은 모델의 말을 그대로 믿고 있었다. 점검 결과 네 군데가 비어 있었다: 실행했다는 명령, 근거로 든 파일, lead가 만든 요구사항, 요청받지 않은 변경. 또 스킬을 실제로 읽었는지 기록되지 않아 "필요한 스킬만 쓴다"를 확인할 수 없었다.

## 결정

모두 토큰이 들지 않는 코드 검사로 하고, 어긋나면 보고서를 반려해 같은 턴에서 고치게 한다(`orchestrator/src/evidence.ts`).

1. **실행한 명령 대조**: builder의 `commandsRun` 각 항목은 그 단계에서 런타임이 실제로 실행한 명령과 맞아야 하고, 종료 코드도 같아야 한다. 실행하지 않은 명령이나 다른 종료 코드를 보고하면 반려.
2. **근거 파일 확인**: 답변(`answer`)과 조사(`research`)의 `sources` 중 파일 경로는 프로젝트 안에 실제로 있어야 한다. URL과 일반 문장은 검사하지 않는다.
3. **요구사항 원문 인용**: build·plan-build의 요구사항마다 `quote`(요청 원문에서 그대로 옮긴 말)를 붙이고, 그 말이 요청에 실제로 있어야 한다. 요청에 없는 테스트·리팩터링·추가 기능을 lead가 지어내는 것을 막는다.
4. **범위 제한**: builder 지침에 "요구사항 밖 변경 금지, 필요한 파일만 읽기"를 넣고, verifier는 요구사항이 필요로 하지 않는 변경을 차단 사유로 본다. plan-build에서는 계획에 없던 파일 변경을 리뷰 프롬프트에 따로 알린다.
5. **스킬 사용 기록**: 세션이 SKILL.md를 열면(Claude의 Read, Codex의 명령) `skill_read` 이벤트와 `RunResult.skillsRead`로 남기고 대시보드에 표시한다. 벤치 과제에 `expect.skills`를 두어 "스킬 선택 정확도(필요한 스킬만)"와 "불필요하게 읽은 스킬 수"를 잰다.
6. **트리거 사례 초안**: `init`이 스킬 초안과 함께 `triggers.json`을 만든다.

## 비용

반려는 같은 턴 안의 재제출이라 추가 세션이 없다. 엄격한 인용 검사로 반려가 늘면 토큰이 조금 늘 수 있으므로, 벤치마크의 보고 반려 횟수와 토큰으로 확인한다.
