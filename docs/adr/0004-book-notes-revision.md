# ADR 0004: 책 정리 노트(Notion '하네스')를 반영한 설계 개정 3

- 날짜: 2026-11-13
- 상태: 결정
- 입력: 사용자가 책을 읽고 정리한 Notion 페이지 '하네스'(팀 구조 6패턴, 스킬 설계, 메타스킬 6단계 파이프라인, 순환 구조)

## 이미 설계에 있던 것 (확인만)

| 노트의 내용 | 설계의 해당 부분 |
|---|---|
| 안쪽은 확률론적, 가장자리는 결정론적 / 실패는 환경 설계 문제 | 핵심 개념 모델, 게이트 |
| PASS/REDO 기준을 객관적으로 고정, 반복 상한 | REDO 규칙(최대 2회, 사유 한정) |
| 스킬 description의 PUSHY 공식, Why-first | 스킬 |
| 팀 규모 3~5명 | 역할 4개 |
| 모델이 에이전트를 부르지 않음(재귀 차단) | `lead`는 위임 도구가 없고 다음 Step은 Workflow가 정함 |

## 새로 반영한 것

1. **팀 구조 선택 기준**: 워크플로를 6패턴에 대응시키고(`build`=파이프라인+생성-검증, `investigate`=팬아웃/팬인), 역할을 늘리는 기준을 4가지(전문성·병렬성·컨텍스트·재사용성)로 제한. 계층적 위임은 2단계까지만, 현재 v2는 1단계(Workflow → 역할)로 고정. 감독자·전문가 풀은 필요가 측정으로 확인될 때만.
2. **스킬 점진적 공개 3층**: (1) description만 항상 맥락에 둠, (2) 트리거되면 SKILL.md 본문, (3) 참조 파일·스크립트는 필요할 때만. description에는 동사 나열·트리거 조건·제외 조건을 모두 적음(셀프 점검 항목에 '제외 조건' 포함).
3. **스킬 검증 절차**: 구조 검증(파일 위치·프론트매터·참조 일관성), 트리거 검증(should-trigger 8~10개 + should-not-trigger 8~10개), 스킬 유무 비교 실행, 정상 1개 + 오류 1개 시나리오. `agent-desk skills check`로 구조 검증을 자동화하고 나머지는 벤치마크 과제로.
4. **역할 정의 파일**: `.agent-desk/agents/<role>.md`(프론트매터: access·effort·skills, 본문: 지침). `config.json`은 런타임 배정·verify·한도만. 사용자 결정(2026-11-13).
5. **`agent-desk init`(프로젝트 현황 검사)**: 도메인·핵심 작업 유형, 기존 에이전트·스킬 현황, 코드베이스 탐색(verify 명령 후보), 사용자 숙련도, 기존 설정과의 충돌을 한 번에 점검. 현재 `doctor`의 초안 생성 기능을 확장.
6. **개선 루프**: 벤치마크·실제 Run의 실패를 원인별로 고칠 곳에 분류한다. 결과물 품질 문제는 스킬, 역할 혼동은 역할 파일, 순서 문제는 워크플로(코드)로. 하네스는 한 번 만들고 끝이 아니라 계속 관리하는 대상으로 취급하고, 6단계에 실패 분석 보고서 형식을 추가.
7. **독립 리뷰의 근거**: "두 명이 한 번씩 보는 것이 한 명이 두 번 보는 것보다 낫다"는 가설을 리뷰 정책 측정의 비교 대상으로 명시(독립 세션 리뷰 vs 같은 세션 자체 점검 vs 리뷰 없음).

## 반영하지 않은 것

- **REDO 2회 후에도 REDO면 경고와 함께 PASS 처리**(책의 생성-검증 패턴): 코드 게이트를 통과하지 못한 결과를 `completed`로 바꾸지 않는다는 원칙과 충돌하므로 `needs_review` 유지(사용자 결정). 비교 후보로만 남기고, 필요하면 같은 벤치마크로 두 방식의 거짓 완료·거짓 경보를 비교한다.
- **메타스킬로 팀을 자동 생성하는 6단계 파이프라인 전체**: 지금 목표(하네스 검증 후 이력서용 측정)에는 과함. 도메인 분석 5항목만 `init`으로 가져옴.
- **팬아웃/팬인 팀의 실시간 교차 검증, 감독자, 전문가 풀**: 에이전트 간 협의를 뺀 결정과 같은 이유로 보류.
